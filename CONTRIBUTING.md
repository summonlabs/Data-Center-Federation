## Code quality expectations

Changes proposed for merge are expected to meet the standards the existing
code is held to.

- Portable C++20. Write standard C++20 that builds with the project's CMake
  build on Windows (MSVC) and on Linux (GCC and Clang), without relying on
  platform-specific extensions or compiler-specific behaviour.
- CMake only. The build is described by CMake; do not introduce a second,
  parallel build system or committed project files for a specific IDE.
- Minimal dependencies. This project intentionally has no third-party
  dependencies. Prefer the standard library. Do not add a dependency unless it
  is genuinely necessary, and justify it in the pull request.
- No first-party compiler warnings. First-party code must be warning-free under
  MSVC /W4 /WX and under GCC and Clang with -Wall -Wextra -Werror and the rest
  of the project's warning set. Warnings from third-party code are not a reason
  to relax these flags.
- Strong types for identities, generations, and quantities. Represent
  identifiers, generation counters, and physical or logical quantities with
  distinct types rather than bare integers, so that incompatible values cannot
  be mixed accidentally.
- Explicit unknown, stale, and conflicting states. Absence and doubt are
  modelled in the type system and reported as such; do not encode "unknown",
  "stale", or "conflicting" as a sentinel value, a default, or a silently
  dropped result.
- Checked arithmetic. Validate ranges and handle overflow, underflow, and
  conversion failures explicitly; do not rely on wrapping or truncation.
- Bounded everything. Queues, buffers, retries, collections, and externally
  supplied sizes are bounded, and untrusted input is validated before it is
  allocated or used.
- No TODO or placeholder code. A change proposed for merge must be complete.
  Do not leave TODO comments, stubs, dead branches, or unfinished paths behind.
- No AI attribution. Do not add AI attribution to commits, code, comments, or
  documentation.

## Workflow

1. Fork the repository and create a topic branch with a short, descriptive
   name.
2. Make your change, keeping it focused on one concern, and follow the code
   quality expectations above.
3. Build the project with CMake, then run the full test suite through ctest in
   both Release and Debug configurations. Both must pass.
4. Add or update tests for any behaviour change. A behaviour change that is not
   covered by a test is not ready to merge.
5. Open a pull request with a concise description of what changed, why it
   changed, and how you verified it, including the configurations you built and
   tested.

## Testing notes

Tests are run plainly. This project does not use test timeouts, watchdog
success logic, or process-kill-as-pass behaviour; a test that hangs is a defect
to diagnose rather than something to abort. Suites that exercise real
independent processes use the in-tree relay to make communication partitions
explicit, and the process is expected to be cleaned up by the suite itself.

## Commit messages

Commit messages must be concise, neutral, and public-facing: a short summary
line describing the change, in plain language suitable for anyone reading the
public history. Do not add AI attribution trailers (such as a Co-authored-by
trailer generated by tooling) and do not add any other unintended co-author
trailers. Credit belongs to the human authors of the change.
